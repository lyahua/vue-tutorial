# 机房 3D 入手教程：从数据到画面

> 目标读者：接手 `idc-three` 的开发者。
> 假设你已经打开了 `/idc-three/room?room=SH-R1`——眼前是上海张江一号机房：
> 贴墙一排空调配电柜、几组面对面机柜阵列、中间扣着玻璃平顶罩的冷通道、
> 每台机柜头上挂着名称牌、柜面上是密密麻麻的 U 位色块。
>
> **这本教程回答四个问题**：
> ① 这些机柜是由什么数据描述的（第一章，最重要）；
> ② 数据怎么变成眼前的画面（第二、三章）；
> ③ 我想增删机柜、挪位置怎么办（第四章）；
> ④ 常用速查（第五章起）。

---

## 一、数据格式：一台机柜在代码里长什么样

整个 3D 机房就是**一棵四级 JSON 树**：`机房 Room → 机柜 Rack → 设备 Device → 配件 Component`。
渲染层的每一块颜色、每一个标签，都能在这棵树上找到出处。

```json
{
  "id": "SH-R1",
  "name": "张江一号机房",
  "siteId": "SH",
  "siteName": "上海机房",
  "gridRows": 9,
  "gridCols": 10,
  "racks": [
    {
      "id": "FAC-SH-R1-1",
      "name": "精密空调",
      "kind": "aircon",
      "row": 0,
      "col": 0,
      "facing": "N",
      "uTotal": 0,
      "status": "normal",
      "devices": []
    },
    {
      "id": "C-08",
      "name": "C-08",
      "kind": "compute",
      "row": 4,
      "col": 7,
      "facing": "S",
      "uTotal": 42,
      "status": "normal",
      "powerKw": 4.35,
      "ratedPowerKw": 10,
      "loadPct": 44,
      "tempIn": 24.1,
      "humidity": 47.2,
      "uUsed": 29,
      "devices": [
        {
          "id": "C-08-U1",
          "rackId": "C-08",
          "name": "SERVER-01",
          "model": "R4900-G2",
          "vendor": "HPE",
          "sn": "SN8A3F1C",
          "category": "server",
          "startU": 1,
          "uSize": 1,
          "status": "normal",
          "components": [
            { "id": "C-08-U1::CPU-1",  "kind": "cpu",  "slot": "CPU-1",  "model": "Xeon Gold 6338", "status": "ok",    "replacedAt": null },
            { "id": "C-08-U1::DISK-0", "kind": "disk", "slot": "DISK-0", "model": "NVMe SSD 1.92TB", "status": "fault", "replacedAt": null }
          ]
        }
      ]
    }
  ]
}
```

### 1.1 Room 机房——决定地板多大

| 字段 | 类型 | 说明 |
|---|---|---|
| `gridRows` / `gridCols` | number | 地板网格行数×列数，**1 格 = 600mm 防静电地板**；地板尺寸 = 列数×0.6m 宽 × 行数×2.3m 深 |
| `racks` | Rack[] | 机柜清单。**数组里没有的 (row, col) 格子就是空地**——不满排、断行、留过道都是"少放几个"自然形成的 |

### 1.2 Rack 机柜——决定站在哪、长什么色

| 字段 | 类型 | 说明 |
|---|---|---|
| `row` / `col` | number | **定位坐标（核心）**：网格第几行第几列，机柜中心落在格子正中 |
| `kind` | string | 柜型，决定柜体颜色：`compute`设备 / `network`网络 / `storage`存储 / `aircon`空调 / `power`配电 / `ups`电池 / `empty`预留 |
| `facing` | `'S'`/`'N'` | 前脸朝向：S=朝+z、N=朝-z。相邻排交替 S/N → 面对面 → 中间自动搭封闭冷通道 |
| `uTotal` | number | U 位数（设备柜 42，设施柜 0） |
| `status` | string | `normal`/`warning`/`alarm`/`offline`——决定柜体材质（告警=红色自发光+顶部信标）和名称牌颜色 |
| `powerKw`/`tempIn`/… | number | 展示指标，悬停信息卡和侧栏直接读 |

### 1.3 Device 设备——决定柜面上哪几格 U 变色

| 字段 | 类型 | 说明 |
|---|---|---|
| `startU` / `uSize` | number | **占用的 U 位**：从 `startU` 起、连占 `uSize` 格；**1U 在底部、自下而上**（和真实机柜一致） |
| `category` | string | 设备类型，决定 U 位色块颜色：`server`青 / `storage`紫 / `network`青绿 / `security`橙 |
| `status` | string | `warning` 的设备在 3D 柜面和 2D 面板上都是黄色 |

### 1.4 Component 配件——换配件弹框的数据源

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | `` `${deviceId}::${slot}` ``，更换接口按它定位 |
| `kind` / `slot` | string | `cpu`/`mem`/`disk`/`psu`/`fan` + 槽位号（如 `DIMM-A1`） |
| `status` | string | `fault` 的配件是"待修复"演示点：换掉它，设备状态会恢复 normal |
| `replacedAt` | number | 最近更换时间戳，null=从未换过；更换接口成功后写回 |

**一句话总结这棵树**：`row/col/facing` 说"站哪、朝哪"，`kind/status` 说"什么颜色"，`startU/uSize/category` 说"柜面哪几格什么颜色"，`components` 说"弹框里能换什么"。

## 二、数据从哪来：api.js 是唯一的门

```
视图组件 ──只 import──→ api.js ──当前──→ ./mock/（本地假数据）
                          │
                          └──将来──→ 真实后端（只改 api.js 函数体，组件零改动）
```

| api.js 导出 | 对应接口 | 谁在用 |
|---|---|---|
| `getGeoJson(adcode)` | GET /idc/geo/{adcode}_full.json | 全国地图（public/geo 本地 GeoJSON） |
| `getMetricsSnapshot()` | GET /idc/metrics | L1 指标条/榜单/告警 |
| `subscribeMetrics(cb)` | SSE 每 2.5s 推送 | L1 实时刷新 |
| `getRooms()` | GET /idc/rooms | 进 room 页缺省机房 |
| `getRoom(roomId)` | GET /idc/room | **room 页直接渲染（无转换层）** |
| `replaceComponent(...)` | POST …/component/{id}/replace | M4 换配件 |

`getRoom` 由 `mock/rooms.js` 产出：台账（mock/geo.js）只配「排×数量 + 告警/离线名单」，
机柜指标和 42U 设备用**固定种子随机**生成（同 id 每次结果一致），再按第一章格式组装——
设施排、断行空位、朝向交替、配件清单都在这一步生成。
**真实项目接后端时**：后端接口直接返回第一章格式的 Room JSON，
api.js 的 `getRoom` 换成 request 调用即可，页面其余部分一字不改。

> 本模块**完全自包含**：拷贝 `idc-three/` 文件夹 + `public/geo/` 地图数据到任何 Vue2 项目即可运行，代码不依赖 idcMap 或其他业务文件夹；额外需要的只有 package.json 里的 `echarts` / `three` / `element-ui` / `dayjs`。

## 三、从数据到画面：渲染链路

### 3.1 第一步：布局坐标 → 世界坐标（room/model.js）

```
网格（业务层）                世界坐标（three 层）
row/col（600mm 一格）  ──→   x = (col + 0.5) × 0.6      机柜中心在格子正中
                            z = (row + 0.5) × 2.3      排距 = 柜深1.1 + 通道1.2
                            y = 2.2 / 2                机柜几何中心，底贴地板

俯视图（对着想象）：
        col=0    col=1    col=2    col=3
row0   [空调]   [配电]   [UPS]              ← 设施排，facing N
row1   (空)     (空)     (空)               ← 空隔
row2   [A-01]  [A-02]  [A-03]  [A-04]      ← facing S（前脸朝下）
row3   [B-01]  [B-02]   (空)   [B-03]      ← facing N（前脸朝上）
                ↑ row2/row3 前脸之间 = 封闭冷通道
```

`+0.5` 是让中心落在格中；y 抬半高是因为 Group 原点在机柜**几何中心**，不抬就半截埋地板。

### 3.2 第二步：一台机柜怎么画（room/three/buildRoom.js）

每台机柜 = 一个 `THREE.Group`（position 就是 3.1 算出的锚点）装四个元素：

```
Group（position = 格子世界坐标 + y 半高）
 ├── body   柜体    BoxGeometry(0.6, 2.2, 1.1) —— 模块级共享几何体
 │                材质按优先级换引用：选中(青光) > 悬停(青光) > 告警(红光)/预警/离线 > 类型色
 ├── face   柜面    PlaneGeometry + CanvasTexture，贴在 facing 那侧柜体表面
 ├── beacon 信标    告警/预警柜顶部长条（正常机柜不建）
 └── label  标签    Sprite 名称牌，悬浮柜顶 +0.3m、始终面向相机、颜色跟状态
```

两个省资源的要点：**几何体全局共享一份**（100 台机柜只有 1 个 BoxGeometry）；**材质按"类型+状态"共享**（hover/选中是换材质引用，不是克隆）。

### 3.3 第三步：柜面 U 位怎么渲染（同一文件里的 drawFaceCanvas）

柜面是一张 **128×512 的 Canvas 画布**，逐格画出来的：

```
画布顶 32px   机柜编号（青色大字）
其余区域      均分成 42 条（1 条 = 1U），从画布底部向上数：
              有设备占用 → 填设备类型色块（server青/storage紫/network青绿/security橙，预警设备黄色）
              空 U     → 画一条青色细线（远看就是参考图那种青色网格）
```

2D 侧栏的 `RackUPanel.vue` 是**同一份数据的另一种画法**：CSS Grid 42 行，设备块按 `起始行 = 42 - 顶U + 1` 跨行摆放——与 3D 柜面共用同一套令牌色和"1U 在底部"约定，两边天然一致。
换配件成功后：2D 靠 Vue 响应式自动变色；3D 调 `refreshRack(rackId)` 在**原画布上重画**并置 `texture.needsUpdate = true`（不重建场景、不丢相机）。

## 四、自定义：增、删、改机柜

数据是唯一事实源，改布局就是改 `racks` 数组，页面刷新即生效。

### 4.1 加一台机柜（或程序化生成）

```js
room.racks.push({
    id: 'A-09',
    kind: 'compute',        // network/storage/aircon/power/ups/empty
    row: 2, col: 8,         // ★ 定位就这两个数：格子没被占就放这
    facing: 'S',            // 'S' 前脸朝+z，'N' 朝-z
    uTotal: 42, status: 'normal',
    devices: [
        { id: 'A-09-U1', category: 'server', startU: 1, uSize: 2, status: 'normal', model: 'R4900-G2' },
    ],
});
room.gridCols = Math.max(room.gridCols, 9);  // 别忘了地板要包住新机柜
```

### 4.2 删一台 / 挪位置

- **删**：从 `racks` 里过滤掉即可，原格子自动变空地（稀疏布局无需善后）；
- **挪**：改 `row` / `col` / `facing` 三个字段，世界坐标由公式重算，不用碰任何渲染代码；
- **换柜型/换状态**：改 `kind` / `status`，颜色由令牌映射自动跟随。

> 当前的数据由 `mock/rooms.js` 的 `getRoom` 生成；要改默认布局，
> 动它里面的生成规则（设施摆放、断行空位、朝向交替都在那儿）。
> M5 会交付可视化布局编辑器（网格拖放改 racks）+ JSON 导入导出，到时不用写代码。

## 五、冷通道是怎么"长"出来的

不用配置——**两排机柜面对面（facing 交替）就自动生成**：

```
zc    = (r1 + 1) × ROW_PITCH        冷通道中心 z（两排前脸正中间）
跨 度 = 这一排机柜占的列范围          顶罩/端门沿 x 的长度
顶 罩 = PlaneGeometry 玻璃平板放平（rotation.x = -π/2）：
        宽 = 通道宽 + 0.6m 外挑，搭在两侧柜顶上方（贴真实封闭冷通道的平顶搭法）
```

配套件：青绿地贴、两端半透玻璃端门、Sprite 温度标签（两侧机柜进风均值）。

## 六、相机与拾取速查

- **三个视角预设**：`camera.js` 的 `preset('overview'|'top'|'front')`，位置由房间包围盒推导；
- **点击机柜飞过去**：`focusRack(id)` → 0.65s easeInOut 补间（补间期间 controls 禁用，防打架）；
- **拖拽 vs 点击**：pointerdown 落点位移 > 5px 判为拖拽视角，不触发点击；
- **悬停节流**：pointermove 只存坐标，渲染循环里每帧最多拾取一次（`picker.flush()`）。

## 七、调试技巧

1. **机柜没显示**：先查 `row/col` 是否超出 `gridRows/gridCols`（在"房间外面"）；再查 `facing` 只能是 'S'/'N'；
2. **柜面文字反了**：facing 'N' 的 face 必须 `rotation.y = Math.PI`（Plane 默认法线朝 +z）；
3. **U 位没对齐**：2D 面板是 CSS Grid（对齐由网格构造保证），别改回绝对定位百分比——踩过 padding box / border 累加两个坑；
4. **想看相机/场景对象**：控制台 `$vm0.$refs.three.scene.camera.position`；
5. **改了不生效**：dev server 重启过吗（vue.config.js / 新增 CSS 变量需要）？浏览器硬刷新（Ctrl+F5）；
6. **性能**：≤200 柜用现状即可（每柜 4 个对象）；上千台再考虑 InstancedMesh 合批。
