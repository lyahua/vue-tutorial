## 五、数据模型、机柜自定义布局与导入导出

### 5.1 核心模型（`room/model.js`，附 JSDoc）

```js
// 机房
Room {
  id: String, name: String, siteId: String,
  gridRows: Number, gridCols: Number,      // 地板网格（600mm 标准一块）
  racks: Rack[]
}
// 机柜
Rack {
  id: String, name: String,
  kind: 'compute'|'network'|'storage'|'aircon'|'power'|'ups'|'empty',
  row: Number, col: Number,                // 网格坐标（布局编辑器产物）
  facing: 'N'|'S',                         // 面向（决定冷通道朝向）
  uTotal: 42                               // U 位数
}
// 设备（挂在机柜上）
Device {
  id: String, rackId: String,
  startU: Number, uSize: Number,           // 42U 从底部 1 起算
  category: 'server'|'firewall'|'switch'|'storage'|'power',
  name: String, model: String, vendor: String, sn: String,
  status: 'running'|'warning'|'offline',
  components: Component[]                  // 可更换配件
}
// 配件
Component {
  id: String, kind: 'cpu'|'mem'|'disk'|'psu'|'fan',
  slot: String,                            // 如 DIMM-A1 / PSU-2
  model: String, status: 'ok'|'fault',
  replacedAt: String                       // dayjs().format() 记录
}
```

### 5.2 机柜位置自定义：稀疏网格模型（已确认支持）

**机柜不是"几行几列摆满"的矩阵，而是稀疏摆放在地板网格上的独立坐标**——`(row, col)` 只是格子索引，放哪个格子哪个格子就有柜子，没放的格子就是空地。因此天然支持：

- **不满排**：某排只有 3 个柜子（col 2~4），其余是预留空位；
- **断行/缺角**：中间留过道、房间尽头留空、异形房间；
- **混合类型**：任意位置放设备柜/网络柜/空调/UPS/配电柜，设施柜不必贴墙；
- **双面朝向**：`facing: N/S` 表达面对面冷通道排列，也支持同向排列。

示例 JSON（一个 10×14 网格、不满排的机房）：

```json
{
  "id": "ROOM-HZ01", "name": "杭州一号机房",
  "gridRows": 10, "gridCols": 14,
  "racks": [
    { "id": "A01", "kind": "aircon",  "row": 1, "col": 1,  "facing": "S", "uTotal": 0 },
    { "id": "A02", "kind": "power",   "row": 1, "col": 2,  "facing": "S", "uTotal": 0 },
    { "id": "R01", "kind": "compute", "row": 2, "col": 3,  "facing": "N", "uTotal": 42 },
    { "id": "R02", "kind": "compute", "row": 2, "col": 4,  "facing": "N", "uTotal": 42 },
    { "id": "R03", "kind": "network", "row": 2, "col": 7,  "facing": "N", "uTotal": 42 },
    { "id": "R04", "kind": "compute", "row": 4, "col": 5,  "facing": "S", "uTotal": 42 }
  ]
}
```

上例中 R02 与 R03 之间（col 5~6）就是空地，第 3 排整排留空——3D 渲染、2D 编辑器、导入导出共用这一份坐标，三种视图天然一致。

**布局编辑（RoomEditor）交互**：
- 画布按网格渲染现有柜子（按 kind 着色），空格子可点选；
- 工具面板选机柜类型 → 点击/拖放到目标格子放置；拖动已有柜子改位置；Delete/右键删除；
- 校验：同格唯一、不越界；`facing` 可切换；
- 保存即写回 `Room.racks` 的 `row/col/facing`，3D 场景重建对应机柜（增量更新，设备数据不丢）。

### 5.3 机柜数据导入导出（已确认覆盖布局本身）

导出内容 = 机房完整快照，**含每个机柜的位置（row/col/facing）、类型、U 位占用、全部设备与配件**，双格式：
（M5 追加：在整房「全量替换」之上，增加**按机柜粒度的增量导入**——见 11.3；跨房腾挪见 11.2。）

| 格式 | 内容 | 用途 |
|---|---|---|
| **JSON**（`{ version, exportedAt, rooms[] }`） | 完整机房：网格尺寸 + racks（含坐标）+ devices + components | 机房备份 / 布局分享 / 编辑器存档；导入按 `version` 做 schema 校验与迁移入口 |
| **Excel**（xlsx） | sheet1「设备台账」：设备 + 所属机柜 + startU/uSize + 配件；sheet2「机柜布局」：机柜 id、类型、row、col、facing、uTotal | 给运维线下维护的资产台账；导入时按 sheet2 还原布局、sheet1 挂载设备 |

导入规则：
- 字段校验（类型枚举、row/col 越界、同格冲突、startU+uSize ≤ uTotal、rackId 悬空引用）；
- 冲突策略由导入向导让用户选：按 `id` **覆盖** or **跳过**；
- **校验失败整单回滚，不允许半量导入**；导入成功后 3D 场景全量重建。

### 6.2 `un-` 前缀组件方案（需求 4.4）

webpack alias 只能改模块路径、改不了模板里的注册名，所以**不可行**；正确做法是写一层透传薄封装，全局注册：

```vue
<!-- components/un/UnButton.vue -->
<template>
  <el-button v-bind="$attrs" v-on="$listeners">
    <slot v-for="(_, name) in $slots" :name="name" :slot="name" />
  </el-button>
</template>
<script>
export default { name: 'UnButton', inheritAttrs: false };
</script>
```

```js
// components/un/index.js —— 全局注册
import UnButton from './UnButton.vue';
// ... UnDialog / UnTable / UnForm / UnFormItem / UnInput / UnSelect /
//     UnOption / UnDrawer / UnBreadcrumb / UnBreadcrumbItem / UnTooltip ...
export default {
  install(Vue) {
    [UnButton /* , ... */].forEach(c => Vue.component(c.name, c));
  }
};
```

收益：业务模板全部写 `<un-button>`；将来真实项目接入自家组件库时，**只改这一层封装，业务代码零改动**。首期按 idcMap 实际用到的组件出封装清单（button/text/breadcrumb/drawer/dialog 等），用到再补。

### 6.3 样式穿透规范（需求 4.3）

统一用 `::v-deep`（Vue2 + sass 下唯一稳妥写法，`>>>` 不支持预处理器、`/deep/` 已废弃）：

```vue
<style scoped lang="scss">
.rack-panel ::v-deep .un-input__inner { border-color: $border-block; }
</style>
```

### 6.4 moment → dayjs（需求 4.6）

- 新代码一律 `import dayjs from 'dayjs'`（已在依赖）；
- 存量 moment 引用全局搜索替换（当前 idcMap 已是 dayjs，预计残留很少）；
- 最后从 package.json 移除 moment，构建验证。

## 八、3D 实现要点（参考交互，代码全部原创）

1. **Vue2 封装模式**：ThreeRoom.vue 在 `mounted` 调 `scene.init(el)`，`beforeDestroy` 严格 `dispose()`（geometry/material/renderer 全链路释放，`window.removeEventListener('resize')`），避免路由往返内存泄漏。
2. **建模**：机柜 = BoxGeometry 按令牌配色分组渲染（同 kind 共享 material/geometry，**按 Rack 的 row/col 稀疏坐标摆放到 600mm 网格上，空格子即空地，不做满排假设**；设备色块以贴在柜面的 PlaneGeometry 表达）；地面网格线 + 冷通道色带；灯盘用 RectArea/环境光即可，**不做 PBR 贴图级拟真**（排除 idc-visual-ops 方案，一是许可风险，二是大屏场景性价比低）。
3. **拾取**：Raycaster 命中机柜 → emit `rack:select`；hover 节流（pointermove 60ms）+ 同步高亮材质（`emissive` 提亮）。
4. **性能**：机柜数量 ≤ 200 时普通 Group 即可；设备不做逐个 mesh（U 位细节交给 2D 面板），单房间 draw call 控制在千级以内；`renderer.setPixelRatio(Math.min(devicePixelRatio, 2))`。
5. **相机**：OrbitControls + 预设位（俯视/正视/环视），点击机柜做 easeInOut 补间聚焦；柜门开合动画（rotationY 0→110°）。
6. **交互闭环**：`rack:select` → 相机聚焦 + 打开 RackUPanel；`device:select` → DeviceDialog 更换配件 → 更新 store → 3D 色块状态即时刷新（设备故障=红色标记）。
7. **降级**：WebGL2 检测失败渲染 WebGLFallback（2D 平面布局 + 同一套 U 位面板，功能不残缺）。

## 十一、需求追加（2026-11-05）：第 6/7/8 点实现方案

> 需求方在需求文档中追加 6/7/8 三点（领导要求考虑）。结论：**三点全部可落地**——
> 7、8 依赖 M5 的画布与校验框架，自然并入 M5；6 独立性强，列为优化项 O1（排 M5 后）。

### 11.1 需求 6：单机房几千个机柜的渲染性能 → 优化项 O1

**现状与瓶颈**（当前实现每柜 4 个对象：body / face 画布 / beacon / label）：
- ~200 柜以内无压力（draw call ≈ 柜数×2，实测流畅）；
- 几千柜时四项都会爆：draw call ×N（WebGL 上限约几千）、**CanvasTexture 显存**（128×512×4 字节 ≈ 256KB/柜，2000 柜 ≈ 500MB）、Sprite 标签逐个渲染、Raycaster 对 N 个 mesh 求交。

**方案：LOD 分级渲染（远简近繁）**
1. **远景（默认进入/俯视）**：全部柜体合成 **1 个 InstancedMesh**（`instanceColor` 按柜型/状态着色，2 个 draw call 搞定全部机柜 + 告警信标）；不生成柜面纹理与标签；
2. **近景**：相机距离阈值内 / 被选中的机柜，动态替换为现有完整 Group（柜面 U 位画布 + 标签）——**复用 M3/M4 已有单柜逻辑，只是按需创建**；
3. **纹理 LRU 缓存**：柜面画布最多保留 ~128 张，超出淘汰最久未用的；
4. **标签策略**：柜数 > 300 时默认隐藏，仅 hover/选中时显示；
5. **拾取**：InstancedMesh 的 raycast 返回 `instanceId` → 映射 rackId，比逐 mesh 求交快得多；
6. **数据侧配套**：`getRoom` 拆两级——概要（racks 坐标/状态，不含 devices）+ 明细（`GET /idc/rack?rackId=` 选中时才取），几千柜的 JSON 也不用一次全拉。

**工作量**：1~2 天；**验收**：2000 柜房间 60fps、显存受控、点选/聚焦/换配件功能不退化。
**为什么排 M5 之后**：M5 编辑器的拖放交互先在当前规模（~40 柜）验证，LOD 改造会动 buildRoom 的组织方式，避免两边同时改。

### 11.2 需求 7：不同机房之间机柜腾挪 → 并入 M5

**可行性高的根本原因**：稀疏网格模型里机柜是**自包含对象**（id/kind/row/col/facing + devices + components 全带在身上），腾挪 = 从 A 房 `racks` 移除 + 加入 B 房 `racks` + 新坐标，不涉及任何数据拆解。

**方案**：
- **接口**：`POST /idc/rack/transfer { rackId, fromRoomId, toRoomId, row, col, facing, reason? }`；
- **mock 持久化**：`transfers` Map（rackId → 目标房间/坐标），`getRoom` 组装时应用覆盖——与 parts.js 的更换记录同一套路；
- **交互**（复用 M5 网格编辑画布，跨房操作 = 同一画布换数据源）：
  机房页工具条「机柜腾挪」→ 选中机柜（侧栏/3D 点选，可多选）→ 选目标机房（un-select 房间列表）→ 在目标机房网格画布点目标格（空格高亮、占用格禁选）→ 确认弹框（源→目标摘要 + 冲突校验）→ 调接口 → 双端刷新；
- **校验**：目标格占用冲突、gridRows/Cols 越界（自动扩地板 or 阻止，二选一，建议阻止并提示）；
- **可选增强**（真实后端阶段）：腾挪审计记录（谁/何时/从哪到哪/原因）、目标机房供电余量提示。

**工作量**：M5 画布就绪后约 1 天。

### 11.3 需求 8：单个机房内按机柜导入数据 → 并入 M5

**与 5.3 整房导入的关系**：整房导入 = 全量替换；按机柜导入 = **增量 merge**——共用 io.js 的解析与校验器，只差冲突策略。

**方案**：
- **入口**：DataIODialog 增加「按机柜导入」tab；
- **模板**：Excel 双 sheet（sheet1 机柜信息：id/kind/row/col/facing/uTotal；sheet2 设备清单：rackId/startU/uSize/category/model/sn/status）或单机柜 JSON 对象；
- **流程**：上传 → 解析预览（树形：机柜 + 其设备/配件）→ 校验 → merge → 只动该机柜，房间内其他机柜零触碰；
- **冲突策略**（导入向导让用户选）：目标房已有同 rackId → **覆盖**（整柜替换含位置设备）or **跳过**；目标格被占 → 阻止并提示改坐标；
- **校验复用 5.3**：U 位重叠/越界、rackId 悬空引用；失败**只回滚该机柜**（整单回滚的机柜粒度版）；
- **接口对应**：`POST /idc/room/{roomId}/rack/import`（body 带 conflict 策略）。

**工作量**：约 0.5~1 天（io.js 校验框架在 5.3 已建）。
