# idc-three 后端对接文档（数据字典 + 接口设计 + 表结构草案）

> 读者：后端开发。目的：依据本文设计库表与接口。
> 前端已全部跑通（当前接本地 mock），本文把 mock 的数据结构与操作**翻译成后端视角**：
> 每个字段是什么意思、为什么这么设计、哪些接口要读写它。
> 前端侧的调用代码见 `api.js`（唯一的接口门），数据生成逻辑见 `mock/` 目录。

## 一、数据全景：一条链

```
地图边界（静态资源，不入库）        站点 site（省级组织维度）
  public/geo/{adcode}_full.json      │
        ↓ 下钻                       ├─→ 机房 room
   （adcode 对齐行政区划码）          │        ├─→ 机柜 rack（稀疏网格坐标）
                                     │        │        ├─→ 设备 device（U 位占用）
                                     │        │        │        └─→ 配件 component（可更换）
                                     │        └─（实时指标：功率/温度/湿度/告警）
                                     └─（全国汇总 summary 由机柜逐级聚合）
```

**核心设计决策（先记住这三条，后面全围绕它）**：

1. **机柜是自包含对象**：`rack` 行上带网格坐标 `(row, col)` + 朝向 `facing`，放哪格哪格有柜子，**没记录的格子就是空地**——"不满排、断行、留过道"不需要任何额外配置。腾挪/导入/布局编辑全是对这张表做增删改。
2. **U 位用区间表达**：设备只存 `startU`（起始 U，1 在底部）+ `uSize`（占几 U），不逐 U 存记录。柜面渲染、U 位面板、导入校验都由区间推导。
3. **静态/动态分离**：站点/机房/机柜位置/设备清单是**资产数据**（低频变更，走写接口）；功率/温度/湿度/告警是**采集数据**（高频更新，走 metrics 接口推送给前端）。同一张 rack 表里两者都出现，建议落库时拆开（见第六节）。

## 二、数据字典（逐字段，含来源）

> **来源图例**（标注每个字段在 mock 侧由谁产生、真实后端侧由谁提供）：
>
> | 标记 | mock 侧（谁生成） | 真实后端侧（谁提供） |
> |---|---|---|
> | 〔台账〕 | `mock/geo.js` 的 SITES 静态配置 | `idc_site` / `idc_room` 表，一次性录入 |
> | 〔生成〕 | `mock/runtime.js` 启动时种子随机**一次性**生成（同 id 每次刷新结果一致） | 初始化入库（CMDB 导入 / 存量表） |
> | 〔游走〕 | runtime 每 2.5s 随机游走更新（页面会动起来的字段） | `idc_rack_metric` 采集表，实时更新 |
> | 〔组装〕 | `mock/rooms.js` getRoom 组装时**推导**（无存储） | 接口层计算 / JOIN |
> | 〔写入〕 | 写接口改写（roomEdits / parts 的 Map 记录） | W1~W4 写接口直接 UPDATE 业务表 |

### 2.1 站点 site —— 对应 mock/geo.js 的 SITES

省级组织单位 + 全国地图散点，一次配置长期不变（真实项目来自 CMDB）。

| 字段 | 类型 | 必填 | 含义 | 来源 |
|---|---|---|---|---|
| `id` | varchar(16) | ✅ 主键 | 站点代号（如 `ZH`/`SH`），前端路由与关联都用它 | 〔台账〕 |
| `name` | varchar(64) | ✅ | 展示名（`上海机房`） | 〔台账〕 |
| `adcode` | varchar(6) | ✅ 唯一 | **行政区划码**（`310000`）——地图下钻的主键，与 GeoJSON 文件名对齐 | 〔台账〕 |
| `province` / `city` | varchar(32) | ✅ | 省市名，省份点击反查 adcode 用 | 〔台账〕 |
| `provinceAdcode` | varchar(6) | ✅ | 所属省 adcode（直辖市时与 adcode 相同） | 〔台账〕 |
| `lng` / `lat` | decimal(10,6) | ✅ | 站点定位点（全国地图散点坐标） | 〔台账〕 |
| `level` | enum | ✅ | `core` 核心 / `region` 区域 / `edge` 边缘（影响 PUE 基准与展示） | 〔台账〕 |
| `pue` | decimal(4,2) | ✅ | 站点能效基准值（如 1.37），机房 PUE 按级别微调 | 〔台账〕 |
| `floor_layout` | JSON / 独立表 | 可选 | **楼层布局**（需求 11 / 2026-11-07 追加）：`[{ roomId, x, z }]`——各机房在站点楼层平面上的摆放坐标（米，原点任意，即房间西北角位置）。站点未配置时接口层可自行排布（前端 mock 为横排 + 3m 走廊）。**推荐 site 表一列 JSON**（一次性台账，无独立查询需求）；或独立 `idc_floor_layout(room_id, x_m, z_m)` 表。房间尺寸 w/d 不用存——由 room 的 gridRows/gridCols 推导 | 〔台账〕 |

> 设计说明：**一个站点绑定一个 adcode**（下钻单位），一个站点下挂多个机房；
> 机房有独立的 `lng/lat`（城市视图里机房是独立点位，站点坐标是省级视图点位）。

### 2.2 机房 room

| 字段 | 类型 | 必填 | 含义 | 来源 |
|---|---|---|---|---|
| `id` | varchar(16) | ✅ 主键 | 如 `SH-R1`，前端路由 query 与全链关联键 | 〔台账〕 |
| `name` | varchar(64) | ✅ | 展示名（`张江一号机房`） | 〔台账〕 |
| `siteId` | varchar(16) | ✅ 外键 | 所属站点 | 〔台账〕 |
| `level` | enum | ✅ | 同站点 level（edge 机房 PUE 会 +0.06） | 〔台账〕 |
| `lng` / `lat` | decimal(10,6) | ✅ | 机房点位（城市视图散点坐标） | 〔台账〕 |
| `gridRows` / `gridCols` | int | ✅ | 地板网格行数×列数（**1 格 = 600mm 防静电地板**） | 〔组装〕由 rack 最大行列推导；真实=W1 保存布局时维护冗余 |
| `ratedPowerPerRackKw` | int | 建议 | 机房级单柜额定功率默认值（新柜入库时兜底） | 〔台账〕 |
| `doors` | JSON / 独立表 | 可选 | **门配置**（2026-11-06 追加）：`[{ wall, offset, width, label? }]`——`wall` 四面墙 `N/S/E/W`；`offset` 门中心沿墙米数（北/南墙从西端量、东/西墙从北端量，与网格共用西北角参考点）；`width` 门宽（单门 1.0 / 双开 1.8）；`label` 门上文字（主入口/应急门…）。**推荐 room 表一列 JSON**（门永远跟房走、无独立查询需求）；要独立建表则 `idc_door(room_id, wall, offset_m, width_m, label)`。校验：wall 枚举 / width 0.3~3m / `0.3 < offset < 墙长-0.3` | 〔台账〕W1 整房导入可更新 |
| `auxiliary` | tinyint(1) | 可选 | **辅助房间标记**（2026-11-08 追加）：`1` = UPS间/配电间/备份间等配套房间（设施排，无 U 位）。**不出现在城市点位图（R2 sites.rooms 过滤）与机房简表（R4 过滤）**——城市点位是"机房"，辅助间进楼层视图（R6 含全部房间）才可见；直链 `GET /idc/room` 仍可访问。缺省 0 | 〔台账〕 |

> ⚠️ mock 里的 `rows: [{row:'A', count:8}]`（排×数量）只是**造数据的配方**，不是位置事实——
> 真实库**不需要**这张排布表。展开过程（前端 mock 三步）：
> ① 配方 `{row:'C', count:8}` → ② 语义定位 `C-08 {row:'C', rowIndex:8}`（排字母+序号）→
> ③ 网格坐标 `C-08 {row:4, col:7, facing:'S'}`（行号=2+排字母下标，列号=序号-1，
> 朝向按排奇偶交替 → 相邻排面对面=冷通道，第二排 col3 留空演示断行）。

> 💡 **墙体不入库**（2026-11-06 追加）：四面墙的位置与长度由 `gridRows/gridCols` 推导
> （房间矩形外沿），高度为前端渲染常量（2.8m 半透玻璃围护）——库里只存"墙上的例外"
> = `doors`。将来出现 L 形机房 / 内隔断墙时才需要把墙升级为数据（`walls` 线段清单）。
> 落库后**位置的唯一事实来源就是 rack 表的 row/col**：编辑保存/导入/腾挪都直接改它，
> 从不回头改"配方"——mock 保留 rows 只因无库环境下每次刷新要重新生成数据。

### 2.3 机柜 rack（核心表）

| 字段 | 类型 | 必填 | 含义 | 来源 |
|---|---|---|---|---|
| `id` | varchar(32) | ✅ 主键 | 机柜编号（`C-08`）。**全局唯一**（腾挪跨房不改 id，跨房定位靠它） | 〔组装〕rooms.js 从台账 rows 展开；真实= `idc_rack` 表（初始化 / W1 / W2 / W3 写入） |
| `roomId` | varchar(16) | ✅ 外键/索引 | 当前所在机房（腾挪 = 改这个字段 + 改坐标） | 同上；W3 腾挪时 UPDATE |
| `name` | varchar(64) | ✅ | 展示名（3D 柜顶名称牌；设备柜通常等于 id，设施柜是「精密空调」等） | 同上 |
| `kind` | enum | ✅ | `compute` 设备机柜 / `network` / `storage` / `aircon` 空调 / `power` 配电 / `ups` 电池 / `empty` 预留。决定 3D 柜体颜色（7 色令牌） | 同上；编辑器/导入可改 |
| `row` / `col` | int | ✅ | **网格坐标**（0 起算，原点在机房西北角，col 东 row 南）。约束：≥0；**(roomId, row, col) 唯一**（一格一柜） | 〔组装〕行号=2+排字母下标、列号=序号-1；真实= `idc_rack` 表，W1/W2/W3 写入 |
| `facing` | enum | ✅ | `S` 前脸朝 +z / `N` 朝 -z。**相邻排交替 S/N = 面对面 = 自动生成封闭冷通道**（3D 渲染规则，后端无需存通道表） | 〔组装〕按排下标奇偶交替；真实=同 row/col |
| `uTotal` | smallint | ✅ | U 位数，设备柜 42、设施柜 0 | 〔组装〕按 kind 判定 |
| `status` | enum | ✅ | `normal` / `warning` 预警 / `alarm` 告警 / `offline` 离线（决定 3D 红色发光体+信标） | 〔生成〕初值按台账 alarmRacks/offlineRacks 名单；〔游走〕未固定柜随温度/负载翻转；真实=采集侧写 `idc_rack_metric` |
| `powerKw` | decimal(8,2) | 采集 | 实测功率（kW） | 〔游走〕±0.12 步长；真实=采集 |
| `ratedPowerKw` | int | 采集 | 额定功率（kW） | 〔台账〕房间级 `ratedPowerPerRackKw` 下发 |
| `loadPct` | int | 采集 | 负载百分比 = powerKw / ratedPowerKw × 100 | 〔游走〕随 powerKw 推导 |
| `tempIn` | decimal(4,1) | 采集 | 进风温度（℃）（冷通道温度标签取两侧机柜 tempIn 均值） | 〔游走〕±0.18 步长，19~34 区间；真实=采集 |
| `humidity` | decimal(4,1) | 采集 | 湿度（%） | 〔游走〕±0.4 步长，35~65 区间 |
| `uUsed` | smallint | 冗余 | 已占 U 数 | 〔组装〕= 该柜 devices 的 uSize 求和；真实=冗余列（导入/编辑时维护） |

> 坐标换算（后端不需要算，仅供理解前端定位）：
> 机柜中心 x = (col+0.5)×0.6 米，z = (row+0.5)×2.3 米（排距 = 柜深 1.1 + 通道 1.2）。

### 2.4 设备 device

| 字段 | 类型 | 必填 | 含义 | 来源 |
|---|---|---|---|---|
| `id` | varchar(64) | ✅ 主键 | 设备编号（mock 用 `{rackId}-U{startU}`，真实后端可用自增/雪花，前端不依赖格式） | 〔生成〕runtime packDevices |
| `rackId` | varchar(32) | ✅ 外键/索引 | 所在机柜（设备不跨柜） | 〔生成〕；腾挪时随 rack 走 |
| `name` | varchar(64) | ✅ | 展示名（`SERVER-01`，画在 U 位色块上） | 〔生成〕`{CATEGORY}-{序号}` |
| `category` | enum | ✅ | `server` / `storage` / `network` / `security`（防火墙等）。决定 U 位色块颜色 | 〔生成〕按权重随机；真实= `idc_device` 表 |
| `model` | varchar | 建议 | 型号（配件弹框展示） | 〔生成〕按 category 从型号池随机 |
| `vendor` | varchar(32) | 建议 | 厂商 | 〔组装〕rooms.js 按 category 映射；真实=CMDB |
| `sn` | varchar(64) | 建议 | 序列号 | 〔组装〕由设备 id 稳定散列生成；真实=CMDB |
| `startU` | smallint | ✅ | 起始 U 位，**1U 在柜底、自下而上**；约束 ≥1 | 〔生成〕自 1 连续排布 |
| `uSize` | smallint | ✅ | 占用 U 数（1~8）；约束 `startU + uSize - 1 ≤ rack.uTotal`，**同柜内 U 区间不重叠**（应用层校验，见 5.3） | 〔生成〕按 category 取规格候选 |
| `status` | enum | ✅ | `normal` / `warning`（预警设备 U 位块变黄；其首块硬盘生成 fault 配件构成修复闭环） | 〔生成〕3% 概率 warning；W4 修复 fault 配件时恢复 normal |

> 防火墙 1CPU+2内存+2硬盘+2电源，交换机 1内存+2电源+2风扇，存储 4硬盘+2电源。
> 建议后端存一张 `component_slot_template` 配置表或入库时展开。

### 2.6 地图边界数据（不入库）

`public/geo/{adcode}_full.json`，阿里 DataV.GeoAtlas 下载后本地化的静态资源（内网无 CDN）。目前 9 份：`100000` 全国 + 8 个机房所在省市。前端 `GET /idc/geo/{adcode}_full.json` 直接触发静态下载，**后端无需接口**；新增机房省市时补一份文件即可。

## 三、读接口（与前端 api.js 一一对应）

| # | 接口 | 说明 | 前端消费方 |
|---|---|---|---|
| R1 | `GET /idc/geo/{adcode}_full.json` | 静态资源（见 2.6） | 全国/城市地图底图 |
| R2 | `GET /idc/metrics` | 全国快照（站点→机房逐级聚合），结构见下 | L1 指标条/地图散点/榜单/告警 |
| R3 | `SSE /idc/metrics/stream` | 每 2.5s 推送一次 R2 同结构快照 | L1 实时刷新 |
| R4 | `GET /idc/rooms` | 机房简表 | 机房切换/腾挪目标选择 |
| R5 | `GET /idc/room?roomId=` | **机房完整模型**（racks+devices+components 一棵树） | 3D 机房页 |

```json
               "uUsed":7416, "uTotal":16464, "powerKw":1987.4, "ratedPowerKw":3360,
               "avgPue":1.39, "alarmCount":18, "offlineCount":4 },
  "sites": [ { "id":"SH", "name":"上海机房", "adcode":"310000", "province":"上海市",
               "lng":121.47, "lat":31.23, "level":"core", "status":"normal",
               "roomCount":2, "rackTotal":92, "rackOnline":91, "uUsed":1783, "uTotal":3864,
               "powerKw":492.1, "alarmCount":2, "offlineCount":1,
               "rooms": [ { "id":"SH-R1", "name":"张江一号机房", "lng":121.6, "lat":31.205,
                            "status":"normal", "rackTotal":48, "powerKw":267.8,
                            "tempAvg":24.1, "pue":1.37, "alarmCount":2 } ] } ],

                "detail":"B-02 进风 28.4℃，超过上限 27℃", "ts":1762300000000 } ],

```
聚合口径：`summary` = sites 累加；site.status = 其机柜最严重状态；alarm 由 rack 状态 + 阈值（tempIn>28 critical / 否则 warning；offline → critical）生成——**可由采集服务推导，不必单独建告警表**（要历史再建）。

**R2 字段级标注（含来源/计算式）**

`summary`（全国汇总，KPI 条数据源）：

| 字段 | 含义 | 来源 / 计算式 |
|---|---|---|
| `siteTotal` | 站点数 | 〔台账〕SITES 计数 |
| `roomTotal` | 机房数 | 〔台账〕各站点 roomCount 累加 |
| `rackTotal` | 机柜总数 | 〔生成〕全部 rackStates 计数 |
| `rackOnline` | 在线机柜数 | 〔游走〕status ≠ offline 计数 |
| `uUsed` / `uTotal` | 已用 U / 总 U | 〔生成〕各柜累加；uTotal = 柜数 × 42 |
| `powerKw` | 总功耗（kW） | 〔游走〕在线柜 powerKw 累加（每 2.5s 变） |
| `ratedPowerKw` | 总额定功率 | 〔生成〕在线柜额定累加 |
| `avgPue` | 平均 PUE | 〔游走〕按各站点 powerKw 加权 |
| `alarmCount` | 告警柜数 | 〔游走〕status=alarm 计数（预警翻转会变） |
| `offlineCount` | 离线柜数 | 〔台账〕offlineRacks 名单计数 |

`sites[]`（站点，地图散点/榜单数据源）——台账字段见 2.1，聚合字段：

| 字段 | 含义 | 来源 / 计算式 |
|---|---|---|
| `roomCount` | 机房数 | 〔台账〕 |
| `status` | 站点状态 | 〔游走〕= 其机柜最严重态（offline>alarm>warning>normal） |
| `rackTotal` / `rackOnline` | 机柜数 / 在线数 | 〔生成〕/〔游走〕计数 |
| `uUsed` / `uTotal` / `powerKw` / `ratedPowerKw` | U 位与功率聚合 | 〔游走〕房级累加 |
| `pue` | 站点 PUE | 〔游走〕房级 powerKw 加权 |
| `tempAvg` / `humidity` | 均温 / 均湿 | 〔游走〕房级均值 |
| `alarmCount` / `offlineCount` | 告警 / 离线柜数 | 〔游走〕/〔台账〕计数 |
| `rooms[].pue` | 机房 PUE | 〔组装〕edge 机房 = 站点 pue + 0.06 |
| `rooms[].其余字段` | 见 2.2 / 聚合同上 | 台账 + 房级聚合 |

`alarms[]`（告警流，点击直达机柜）：

| 字段 | 含义 | 来源 / 计算式 |
|---|---|---|
| `id` | 告警 id | 〔组装〕`{rackId}-offline` 或 `{rackId}-alarm` |
| `siteId` / `siteName` / `roomId` / `rackId` | 归属定位 | 〔生成〕机柜所属链路（跳转定位用） |
| `level` | 严重级别 | 〔组装〕offline→critical；alarm 柜 tempIn>28→critical 否则 warning |
| `title` / `detail` | 标题 / 详情 | 〔组装〕ALARM_TEMPLATES 模板（温度/功率/失联三选一） |
| `ts` | 告警时间戳 | 〔组装〕offline 固定 9 分钟前；alarm 按 rackId 稳定散列 0~480s 前（排序稳定不跳动） |

**R4 返回 `Array<RoomBrief>`**（机房简表，字段级标注）：

| 字段 | 含义 | 来源 |
|---|---|---|
| `id` / `name` / `siteId` / `siteName` | 机房标识与归属 | 〔台账〕见 2.2 |
| `rackTotal` | 机柜数 | 〔生成〕该房 rackStates 计数 |

## 四、写接口（全部是"确认事件"式，无权限要求——需求 2.2 确认）

### W1 布局编辑器保存（全量替换）
`POST /idc/room/{roomId}/layout`，body = `{ racks[], doors? }`——机柜完整数组（含 row/col/facing/kind/devices）+ 可选门配置（整房导入时携带；缺省保留库中已有门，见 2.2 doors 字段）。
- **语义**：事务性全量替换——库里该房机柜以本次提交为准（少的删除、有的 upsert）；doors 传了则一并替换；
- racks 中的 `name` / `uTotal` / `kind` 可能被布局编辑器的「机柜属性编辑」修改过（2026-11-09 上线）——字段本身同 R5，落库以提交值为准；
- **校验**（不通过返回 4xx + 错误列表，整单回滚）：同格冲突 / 坐标越界 / **房内机柜 ID 唯一** / **名称非空** / U 位越界重叠（见 5.3）/ 设施柜挂设备（见 5.3）/ 门 wall 枚举与 width 0.3~3m；
- 前端保存前已本地拦截以上全部规则，后端兜底；
- **导入模板与格式样例**：前端项目 `src/pages/idc-three/example/` 下有四份（整房导入/按机柜导入 × JSON/Excel），Excel 表头与解析列名严格一致，后端做测试数据可直接参照。
- **请求示例**：`{ "racks": [ …R5 的 racks 数组原样回传 ] }`
- **响应**：`{ "code": 0 }`（失败走 HTTP 4xx + `{"errors":["同格冲突：…"]}`，整单回滚）

### W2 按机柜导入（需求 8，增量合并）
`POST /idc/room/{roomId}/rack/import`，body = `{ "rack": {…单柜完整对象}, "conflict": "overwrite" | "skip" }`。
- rackId 已存在：`overwrite` 整柜替换（含位置与设备） / `skip` 跳过；
- 目标格被其他柜占用 → `code:1 + msg`（前端也预校验）。
- **请求示例**：
  ```json
  { "rack": { "id": "C-08", "kind": "compute", "row": 4, "col": 7, "facing": "S",
              "uTotal": 42, "status": "normal", "devices": [ … ] },
    "conflict": "overwrite" }
  ```
- **响应**：`{ "code": 0, "action": "added" }`（或 `"replaced"` / `"skipped"`；失败 `{"code":1,"msg":"目标格 (4,7) 已被占用"}`）

### W3 机柜跨房腾挪（需求 7）
`POST /idc/rack/transfer`，body = `{ rackId, fromRoomId, toRoomId, row, col, facing }`。
- **落库**：`UPDATE rack SET room_id=toRoomId, row, col, facing`（id 不变，设备配件跟随）；
- 校验目标房 (row,col) 未占用；
- **建议**写审计表 `rack_transfer_log`（谁/何时/从哪房哪格 → 哪房哪格）。
- **请求示例**：`{ "rackId": "C-08", "fromRoomId": "SH-R1", "toRoomId": "SH-R2", "row": 2, "col": 5, "facing": "S" }`
- **响应**：`{ "code": 0 }`（失败 `{"code":1,"msg":"目标格 (2,5) 已被占用"}`）

### W4 更换配件（需求 2.2 / M4）
`POST /idc/device/{deviceId}/component/{componentId}/replace`，body = `{ "model": "新型号" }`。
- 落库：`UPDATE component SET model, replaced_at=NOW()`；**fault 件修复时同步 `device.status='normal'`**；
- 建议写 `component_replace_log`（审计：谁/何时/换了什么/旧新型号）。
- **请求示例**：`{ "model": "NVMe SSD 3.84TB" }`
- **响应**：`{ "code": 0, "data": { "model": "NVMe SSD 3.84TB", "replacedAt": 1762300000000 } }`

> W1/W2/W3 共同点：**前端都先在本地校验并弹框确认**，接口是最终确认事件；
> 失败语义统一「整单回滚」（layout/import）或「拒绝执行」（transfer 返回 code=1）。

## 五、导入导出格式（Excel / JSON，文件由前端生成，后端可复用校验规则）

### 5.1 JSON 快照
```json
{ "version": 1, "exportedAt": "2026-11-05 14:00:00", "rooms": [ {…Room 完整对象} ] }
```
用途：备份/还原（导出→清空→导入完全还原）。`version` 是 schema 迁移入口。

### 5.2 Excel 双 sheet（中文表头，运维线下维护友好）

**sheet「机柜布局」**：`机柜ID | 类型 | 行 | 列 | 朝向 | U位数 | 状态`
**sheet「设备台账」**：`所属机柜 | 设备ID | 名称 | 类型 | 型号 | SN | 起始U | 占用U数 | 状态`

单机柜导入 = 机柜布局 sheet 只有一行（+ 该柜的设备行）。

### 5.3 校验规则清单（io.js 现成实现，后端可直接抄成语义）

1. 机柜 ID 非空；类型 ∈ 7 枚举；row/col 为 ≥0 整数；朝向 ∈ {S, N}；U位数 ∈ [0,48]；
2. **房内机柜 ID 唯一**（W1 提交中不得重复——主键天然约束，后端落库兜底）；
3. **机柜名称非空**（≤32 字建议；2026-11-09 属性编辑引入的前置校验）；
4. **同格冲突**：同房内 (row, col) 不能有两台柜；
5. U 位越界：`startU ≥ 1` 且 `startU + uSize - 1 ≤ uTotal`（含「U 位收缩」：编辑器把 uTotal 改小于设备最高占用 U 时命中本条拦截）；
6. U 位重叠：同柜内设备 U 区间互不重叠（按 startU 排序后相邻判断）；
7. 设施机柜（uTotal=0）不允许挂设备；
8. 校验失败 → 返回全部错误（前端列表展示），**禁止导入**。

## 六、表结构草案（MySQL 风格 DDL，字段名按后端惯例微调）

```sql
-- 站点（静态台账）
CREATE TABLE idc_site (
  id            VARCHAR(16)  PRIMARY KEY,
  name          VARCHAR(64)  NOT NULL,
  adcode        VARCHAR(6)   NOT NULL UNIQUE,
  province      VARCHAR(32)  NOT NULL,
  city          VARCHAR(32)  NOT NULL,
  province_adcode VARCHAR(6) NOT NULL,
  lng           DECIMAL(10,6) NOT NULL,
  lat           DECIMAL(10,6) NOT NULL,
  level         VARCHAR(8)   NOT NULL,          -- core/region/edge
  pue           DECIMAL(4,2) NOT NULL
);

-- 机房
CREATE TABLE idc_room (
  id            VARCHAR(16)  PRIMARY KEY,
  name          VARCHAR(64)  NOT NULL,
  site_id       VARCHAR(16)  NOT NULL,
  level         VARCHAR(8)   NOT NULL,
  lng           DECIMAL(10,6) NOT NULL,
  lat           DECIMAL(10,6) NOT NULL,
  grid_rows     INT NOT NULL,                   -- 由 rack 推导维护
  grid_cols     INT NOT NULL,
  rated_power_per_rack_kw INT DEFAULT NULL,
  KEY idx_site (site_id)
);

-- 机柜（核心表：位置 = row/col，一格一柜）
CREATE TABLE idc_rack (
  id            VARCHAR(32)  PRIMARY KEY,
  room_id       VARCHAR(16)  NOT NULL,
  name          VARCHAR(64)  NOT NULL,
  kind          VARCHAR(8)   NOT NULL,          -- compute/network/storage/aircon/power/ups/empty
  grid_row      INT NOT NULL,                   -- 前端字段 row
  grid_col      INT NOT NULL,                   -- 前端字段 col
  facing        VARCHAR(1)   NOT NULL,          -- S/N
  u_total       SMALLINT     NOT NULL DEFAULT 42,
  u_used        SMALLINT     NOT NULL DEFAULT 0,
  status        VARCHAR(8)   NOT NULL DEFAULT 'normal',
  power_kw      DECIMAL(8,2) DEFAULT NULL,      -- ↓ 采集字段：建议拆到采集表
  rated_power_kw INT DEFAULT NULL,
  load_pct      INT DEFAULT NULL,
  temp_in       DECIMAL(4,1) DEFAULT NULL,
  humidity      DECIMAL(4,1) DEFAULT NULL,
  UNIQUE KEY uk_room_cell (room_id, grid_row, grid_col),
  KEY idx_room (room_id)
);

-- 设备（U 位区间）
CREATE TABLE idc_device (
  id            VARCHAR(64)  PRIMARY KEY,
  rack_id       VARCHAR(32)  NOT NULL,
  name          VARCHAR(64)  NOT NULL,
  category      VARCHAR(8)   NOT NULL,          -- server/storage/network/security
  model         VARCHAR(64)  DEFAULT NULL,
  vendor        VARCHAR(32)  DEFAULT NULL,
  sn            VARCHAR(64)  DEFAULT NULL,
  start_u       SMALLINT     NOT NULL,
  u_size        SMALLINT     NOT NULL,
  status        VARCHAR(8)   NOT NULL DEFAULT 'normal',
  KEY idx_rack (rack_id)
);

-- 配件（可更换）
CREATE TABLE idc_component (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  device_id     VARCHAR(64)  NOT NULL,
  kind          VARCHAR(8)   NOT NULL,          -- cpu/mem/disk/psu/fan
  slot          VARCHAR(16)  NOT NULL,
  model         VARCHAR(64)  NOT NULL,
  status        VARCHAR(8)   NOT NULL DEFAULT 'ok',   -- ok/fault
  replaced_at   DATETIME     DEFAULT NULL,      -- null=从未更换
  UNIQUE KEY uk_device_slot (device_id, slot)
);

-- 腾挪审计（建议）
CREATE TABLE idc_rack_transfer_log (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  rack_id       VARCHAR(32) NOT NULL,
  from_room_id  VARCHAR(16) NOT NULL,
  to_room_id    VARCHAR(16) NOT NULL,
  to_row        INT NOT NULL, to_col INT NOT NULL, facing VARCHAR(1),
  operator      VARCHAR(32), ts DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 配件更换审计（建议）
CREATE TABLE idc_component_replace_log (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  component_id  BIGINT NOT NULL,
  old_model     VARCHAR(64), new_model VARCHAR(64),
  operator      VARCHAR(32), ts DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

**采集数据建议**：`power_kw / temp_in / humidity / status` 高频变更，建议单独一张
`idc_rack_metric`（rack_id 主键 + 采集字段 + update_time），由采集服务秒级/分钟级更新；
R2 接口实时 JOIN 聚合。要历史曲线再上时序库（InfluxDB/TDengine），本期前端无此需求。

## 七、枚举字典（含义 / 颜色 / 增减改动点）

> 颜色全部走设计令牌（`styles/_tokens.scss`，换色只改那一处）；后端落库建议

### 7.1 rack kind 柜型（决定 3D 柜体颜色，7 值）

| 取值 | 含义 | 前端颜色（令牌 `--idc3-rack-*`） |

| `network` | 网络机柜（交换机/路由器） | 深青蓝 `#2c5a6e` |

**加/减一个柜型的改动点**（例：加 `gateway` 网关柜）：

5. 后端：字典表加一行 + DDL 注释更新。**删除**同理反向，且必须先迁移存量数据
   （`UPDATE rack SET kind='compute' WHERE kind='gateway'`），否则校验直接报"未知柜型"。

**加/减一个状态的改动点**（状态是采集侧写的，加值如 `maintain` 维护中）：

### 7.3 device category 设备类型（决定 U 位色块颜色，4 值）

| `storage` | 存储设备 | 紫 `#8b5cf6` |

**加/减一个设备类型的改动点**（category 额外带"配件槽位模板"，改动面最大）：
1. 令牌：`$idc3-dev-xxx` + 输出；
2. `room/model.js`：`DEV_CATEGORY_LABEL` + **`PART_SPECS` 加该类型的配件槽位模板**
   （缺了它换配件弹框是空的）；
3. `room/components/RackUPanel.vue`：`DEV_CATEGORIES` 图例数组加项；
4. mock 造数据：`constants.js` `DEVICE_TYPES` 权重池 + `mock/rooms.js` `VENDOR_BY_CATEGORY`；
5. `room/three/buildRoom.js` `drawFaceCanvas` 的 U 位色 fallback；后端：字典 + 型号池。

### 7.4 其余枚举（无颜色或颜色语义简单）

| 枚举 | 取值 | 含义 | 颜色 | 加/减改动点 |
|---|---|---|---|---|
| site/room `level` | `core`/`region`/`edge` | 核心/区域/边缘站点（影响 PUE 基准：edge 机房 pue+0.06） | core 站点在 L1 地图用**荣誉金描边** `#d4a24c`（等级 ≠ 状态，红色只留给告警） | 台账 + runtime 的 pue 微调 + 地图金圈逻辑 |
| `facing` | `S` / `N` | 前脸朝南(+z) / 朝北(-z)；相邻排交替 = 封闭冷通道 | 无（几何语义） | 纯几何约定，**不建议加值**；要加需改 buildRoom 的 face 贴面方向逻辑 |
| device `status` | `normal` / `warning` | 正常 / 预警（U 位块变黄；预警设备首块盘生成 fault 配件） | warning 复用 `--idc3-status-warning` | STATUS_LABEL + mock 3% 概率 + 3D 画布 fallback |
| component `kind` | `cpu`/`mem`/`disk`/`psu`/`fan` | CPU/内存/硬盘/电源/风扇（配件表格行） | 无色（表格文字） | `model.js` `PART_KIND_LABEL` + `PART_MODEL_POOL` 型号池 + `PART_SPECS` 槽位引用 |
| component `status` | `ok` / `fault` | 正常 / 故障（fault 件更换后设备恢复 normal） | fault 在弹框里用告警红 | 演示闭环逻辑在 rooms.js buildComponents + DeviceDialog 确认链 |
| import `conflict` | `overwrite` / `skip` | 按机柜导入遇同 ID：整柜覆盖 / 跳过 | 无（UI 单选按钮态） | W2 语义 + DataIODialog 策略按钮，前后端需同步 |
| alarm `level` | `critical` / `warning` | 严重（离线/高温）/ 预警 | critical 红、warning 橙（复用状态令牌） | runtime 推导规则 + AlarmFeed 标题色 |

### 7.5 加减枚举的通用五步（任何枚举都适用）

1. **令牌**：`_tokens.scss` 加/删颜色 + `index.scss` 输出（有颜色的枚举）；
2. **字典**：对应的 `*_LABEL` / `KINDS` / `SEVERITY` 常量（`model.js` / `constants.js`）；
3. **消费方**：grep 枚举值字符串，把 if 链/排序表/图例数组补齐（buildRoom、RackUPanel、index.vue）；
4. **mock**：造数据的池子/名单同步（runtime/rooms/constants）；
5. **后端**：字典表加行 + 采集/校验逻辑 + **存量数据迁移脚本**（删除枚举时必须）。
判断改动是否齐了的方法：全局 grep 该枚举值——前端 + mock + DDL 注释三处都出现即闭环。

## 八、接口切换指南（mock → 真实后端，只改 api.js 一个文件）

> **总原则：`api.js` 是唯一的合同。** 组件只 import api.js、只认它每个函数的
> **返回结构**（即本文第二、三节的字段表）；mock 只是垫在合同底下的当前实现。
> 换后端 = 把 mock 从底下抽掉、换成 request 调用——**合同一字不改，页面零改动**。
> 换完整个 `mock/` 文件夹可以删除。

### 8.1 逐函数对照（改哪里、契约在哪、后端路径）

| api.js 函数 | 现在的实现（mock） | 返回结构契约 | 真实后端 |
|---|---|---|---|
| `getGeoJson(adcode)` | fetch 本地 GeoJSON | GeoJSON FeatureCollection | 静态资源，无需后端 |
| `getMetricsSnapshot()` | mock/runtime `getMetrics` | 第三节 R2 `Metrics` | `GET /idc/metrics` |
| `subscribeMetrics(cb)` | mock/runtime `subscribe` | 同 R2，2.5s/次 | `SSE /idc/metrics/stream` |
| `getRooms()` | mock/runtime `listRooms` | 第三节 R4 | `GET /idc/rooms` |
| `getRoom(roomId)` | mock/rooms `getRoom` | 第二节 2.2~2.5 的 Room 树 | `GET /idc/room?roomId=` |
| `saveRoomLayout(roomId, racks)` | mock/roomEdits | 入参 = Room 树的 racks | `POST /idc/room/{id}/layout` |
| `importRack(roomId, rack, opts)` | mock/roomEdits | `{code, action, msg?}` | `POST /idc/room/{id}/rack/import` |
| `transferRack(payload)` | mock/roomEdits | `{code, msg?}` | `POST /idc/rack/transfer` |
| `replaceComponent(...)` | mock/parts | `{code, data:{model, replacedAt}}` | `POST /idc/device/{id}/component/{id}/replace` |

### 8.2 场景一：后端按文档字段实现（最省事，函数体直换）

```js
// —— 现在的 api.js ——
import { getMetrics, listRooms, subscribe } from './mock/runtime';
export function getMetricsSnapshot() {
    return getMetrics();
}

// —— 换成（其余什么都不动）——
import request from '@/utils/request';
export function getMetricsSnapshot() {
    return request.get('/idc/metrics');
}
```

SSE 的换法（返回的解绑函数照旧）：

```js
export function subscribeMetrics(listener) {
    const es = new EventSource('/idc/metrics/stream');
    es.onmessage = e => listener(JSON.parse(e.data));
    return () => es.close(); // 页面离开时照常调用，语义与 mock 版一致
}
```

### 8.3 场景二：后端字段名和文档不一样（在 api.js 里做映射）

**永远不要让组件去适配后端字段**——映射写在 api.js 函数体里，吐出来的还是契约结构：

```js
export function getRoom(roomId) {
    return request.get('/idc/room', { params: { roomId } }).then(backend => ({
        id: backend.roomId,                                  // 后端叫 roomId → 契约叫 id
        name: backend.roomName,
        siteId: backend.siteId,
        siteName: backend.siteName,
        gridRows: backend.gridRows,
        gridCols: backend.gridCols,
        racks: backend.cabinetList.map(c => ({               // 后端叫 cabinetList → 契约叫 racks
            id: c.cabinetNo,                                 // 后端叫 cabinetNo → 契约叫 id
            row: c.gridRow,                                  // 网格行，0 起算整数（见 2.3）
            col: c.gridCol,
            facing: c.facing,
            devices: (c.deviceList || []).map(d => ({
                id: d.deviceNo,
                startU: d.startU,
                uSize: d.uSize,
                category: d.deviceType,
            })),
        })),
    }));
}
```

映射写在一个函数里，字段对不上**只改这一处**，30 个组件零感知——这就是当初把
所有 import 收口到 api.js 的原因。

### 8.4 场景三：后端结构完全对不上（先谈接口再写码）

如果后端的返回结构连"树形"都不是（比如 rack/device 分两个接口返回扁平列表），
仍可在 api.js 里用 `Promise.all` 拉两个接口、自己 JOIN 成契约的 Room 树再返回。
**判断标准始终只有一条：api.js 吐出来的结构 = 本文档第二、三节的字段表。**

### 8.5 换完的清理清单

1. 删除 `mock/` 文件夹（geo/runtime/rooms/roomEdits/parts 全部不再被引用）；
2. api.js 顶部 import 从 `./mock/*` 换成 request/EventSource；
3. `room/model.js`、组件、three 层**一行都不用动**；
4. 自测路径：L1 地图有数据 → 点省下钻 → 点机房进 3D → 换个配件 → 挪个柜子——
   这条链全通就说明合同没破。

## 附：mock 与真实实现的对照（帮后端理解前端在等什么）

> ⚠️ **先看这条（避免混淆）**：`mock/runtime.js` 里的 rack 对象（`row: 'C'` 字母 +
> `rowIndex` + `x/z/rot` 物理坐标）是**造数据的引擎内部中间产物**，不是接口契约——
> 它只在 mock 模块间流转（runtime 生成 → rooms.js 组装），**后端不需要实现这层**。
> 接口契约以本文第二、三节的字段表为准：rack 的 `row/col` 永远是 **0 起算的数字**。
>
> 内部字段去向：`row`字母+`rowIndex` → rooms.js 展开为数字 `row/col`（见 2.2 注）；
> `x/z/rot` → 2D 平面图遗留，组装时**直接丢弃**；指标字段 → R2 聚合 + R5 透传；
> `devices` → 转 `startU/uSize/category` 并生成配件。

| 前端 mock 文件 | 模拟的真实后端 | 说明 |
|---|---|---|
| `mock/geo.js`（SITES 台账） | `idc_site` / `idc_room` 表 | 静态资产，低频变更 |
| `mock/runtime.js` | 对外导出 `subscribe/getMetrics`（→R2/R3 契约 ✓）、`listRooms`（→R4 ✓）；**内部导出 `getRoomRacks` 只是给 rooms.js 的传球，无契约** | 动态指标 + 采集服务 |
| `mock/rooms.js`（getRoom 组装） | R5 `GET /idc/room` | 三棵树 JOIN 成一棵 |

| `mock/parts.js`（更换记录 Map） | W4 + `idc_component_replace_log` | 同上 |
